# Maverick 0.1 — development target, not shipped release notes

**Current product version:** `0.1.0-dev`  
**Selected codename:** Maverick  
**Intended qualified display:** FroodzOS 0.1 Maverick — ARM64 Alpha  
**Initial experimental board:** Lenovo 83N3 / IdeaPad Slim 3 15Q8X10,
Snapdragon X1-26-100  
**Qualified artifact / release date:** none established / not assigned

## Intended alpha scope

A board-specific experimental live baseline with native boot, usable declared
console/input/network workflow, documented hardware gaps, bounded thermal/power
operation, actual safe shutdown and tested recovery. Establish exact artifact
provenance, authentication and legal/publication clearance. This is not a claim
of a finished installer, every ARM64 board, accelerated desktop, all peripherals
or native AI-workstation acceptance.

Accepted different-boot HOME persistence is retained. Installed application,
settings and tool persistence remains a different gate. Hermes can land in
Maverick, but may only be advertised as usable after its own source, process
lifecycle, package, integration and owner-native acceptance gates pass. The later
Hellcat milestone is not a reason to defer current Hermes engineering.

## Retained observations and unmet exit criteria

[CURRENT.md](CURRENT.md) records observed native boot/console/Wi-Fi,
owner-observed input/software-rendered desktop and accepted HOME proof. It also
records unaccepted touchpad/graphics/audio/camera/power/suspend/recovery behavior,
actual privileged timeout/cancel failure, rejected directory/bundle revisions
and the unadmitted bundle-v2 / ordinary-user lifecycle prototype progress.
These are blockers/limitations, not alpha success checkmarks. Any release scope
change requires an explicit decision and accurate support matrix.

Before creating a qualified `0.1.0-alpha.1` candidate/tag or delivering a newly
labelled image, satisfy all applicable [POLICY.md](POLICY.md) gates for the exact
candidate and obtain the required owner authorization. Keep independent fixture,
source/tool, runtime/package, physical delivery and native acceptance decisions
separate. No date, binary download, tag or new build manifest is created here.

## What this metadata work changes

Only local source documentation, machine-readable development identity and a
read-only consistency validator with inert tests. It does not mutate a working
boot environment, persistence markers, frozen accepted tools, `/etc/os-release`,
USB media, firmware, global provider/model settings or any publication target.
