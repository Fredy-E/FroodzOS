# dt24: keyboard dependency repair and normal systemd text boot

## Scope

User approved implementation and the existing file-only USB update scope. The build-time repair candidate has now passed native interactive text acceptance; see [native success evidence](dt24-native-text-success.md). This does not establish Plasma or full hardware support. No display/GPU re-enable, internal-disk writes, formatting, BIOS/BCD/boot-order changes, or firmware-variable clearing is included.

## Implemented changes

- Numbered patch `0019-diagnostic-keyboard-i2c9-dependencies.patch` restores the configured keyboard's existing fixed 3.3 V rail and GPI1 DMA provider, and removes only I2C9's dead ICC properties. Bus voting is skipped diagnostically; this is local bring-up, not an upstream/production ICC solution.
- Compiled DT changes are constrained to four properties. Kernel Image, voltages, GPIO/IRQ, DMA channels/mask, IOMMU, existing USB repair, GEM/display/PCIe/NVMe disables remain unchanged.
- I2C-HID core, OF frontend and generic HID are explicitly included and early-loaded, with a new independently tested module gate.
- New independent `kestrel_text` hook is inert unless `kestrel_textboot=1`. It stages a local getty-based diagnostic login program into the RAM overlay, selects multi-user target and masks SSH/SDDM units. It never changes the squashfs or account/password files.
- The local diagnostic shell is intentionally unauthenticated like the earlier PID1 recovery shell, but it is now a child of normal systemd/getty rather than PID1. This is not a production login configuration.
- An actual interactive Bash startup writes `06-text-startup.txt`; entering `kestrel-proof` writes `07-typed-command.txt`. Both are gated on the same validated USB mount, exact boot ID, USB ancestry and marker. No arbitrary keystroke capture is added.
- Prepared menu keeps 11 entries and default number 8. Entries 8/9 use normal init, systemd multi-user target and an explicit VT. Entry 8 reduces screen flooding; entry 9 retains verbose diagnostics and confirmation.
- Original logger/checkpoint hooks, binaries and PID1 diagnostic wrapper are byte-identical to dt23. Firmware capture remains bounded and separately enabled as before; no firmware variables have been written/cleared from Windows.

## Virtual acceptance

The corrected default-entry EFI/systemd/getty test passes with actual serial input, recovered startup/typed-command proof files, active multi-user target, all required runtime modules, userspace journal and normal shutdown. This proves the virtual serial userspace path, not native VT or physical I2C input. The initial ttyAMA0 wait resolved during device coldplug; it was not a candidate failure. The first test run matched a menu instruction as a prompt and sent too early; it is retained as failed harness evidence, and the fresh v2 run uses an anchored prompt predicate. Quiet kernel startup is checked in captured kmsg rather than requiring a filtered serial banner.

Independent read-only reviews and packed-hook/predicate fixtures pass. The disposable EFI regression passed flag-off, no-USB timeout capture, persistence recovery in a new VM process, and refusal to overwrite existing records. These tests made zero physical firmware writes.
